# 跨进程读取一致性

## 现状

H5 后端把飞书各表全量刷进**进程内**快照 `_snapshot`，后台循环按 `_SNAPSHOT_INTERVALS` 刷新：likes/messages 20s、signups 45s、users 60s、activities 180s、observers/group_selections/group_results 300s（分组表仅在该活动「收集中」时按 300s，否则退到 600s）。每表另有 `_SNAPSHOT_STALE` 过期阈值：likes/messages 60s、signups 90s、users 120s、activities/observers/group_selections/group_results 600s。

**bot 与 H5 是两个进程，内存不共享**：活动状态（`分组状态`、分组功能开启）、分组结果、各类开关全由 bot 写入，H5 只读。H5 写完调 `refresh_snapshot_table_async` 只刷新自己进程内那份，对 bot 毫无作用——跨进程可见性只能靠 H5 重新读飞书。

## 规则一：决定性读取必须实时读

**任何端点，只要判定结果依赖 bot（或其他进程）写入的数据——活动状态、分组结果、各类功能开关——必须实时读飞书，不得吃周期快照。**

判定读取吃快照的代价不是「慢一点」而是**判错**：分组状态刚改成「收集中」，H5 快照还是「未开始」，用户点提交志愿就被拒，最长 300s。

- `_snap_fresh(key)` / `snap_*(..., fresh=True)`：不管过没过期都实时读一次并回填。**决定性读取一律用这个。**
- `_snap_live(key)`：快照未就绪或过 `_SNAPSHOT_STALE` 时实时读一次**并回填**（自愈），不会每个请求都打飞书。

已实时的分组流程端点：`group/candidates`、`group/select`、`group/status`、`group/result`、`/api/activities/mine/groups`。

## 实时读的失败冷却

`refresh_snapshot_table` 只在成功时刷新 `_snapshot_last_ok`，失败时旧时间戳留着；而 `_snap_live` / `_snap_fresh` 每次请求都会因「快照过期」再读一次飞书——飞书持续故障或限流（429）时，等于用请求量放大限流，正好是快照要避免的雪崩。

因此失败会拉起该表的冷却：`SNAPSHOT_FAIL_COOLDOWN = 30` 秒，期间 `_snap_live` / `_snap_fresh` 直接返回现有快照、**不打飞书**（此时飞书本就不可用，返回陈旧快照是唯一合理降级），到期自动重试，不是永久熔断；任何一次读成功立即解除。取 30 秒：飞书限流窗口通常在 1 分钟内，30 秒足够等到恢复又不至于长时间吃陈旧；且不小于任何一个 `_SNAPSHOT_STALE`（最短 likes/messages = 60s），不会额外拉长已有的陈旧上限。冷却只压失败重试，**不压成功路径**，自愈不受影响。

## 规则二：新跨进程写入功能，先在读取侧解决

优先在**读取侧**解决（判定处改实时读）。不要靠调小快照间隔（拿飞书配额赌一致性，且全局生效、误伤所有读路径），也不要先想加失效通道（跨进程协议，复杂度和故障面大一个量级）。

## 规则三：快照只用于展示类读取

只用于「展示类、低频、可容忍陈旧」的读取：卡片列表、我的报名列表、留言数等。陈旧只影响观感、不影响判定，也不该让用户重试才能推进。

回填快照**必须是全表形状**（统一走 `_SNAPSHOT_FETCHERS[key]` 的 `raw_search_records`），绝不能把 `get_group_results(act_id)` 这类按活动过滤过的结果写回全局快照，否则会污染成「只有某个活动的数据」。

## 什么时候才考虑统一失效通道（bot → H5 通知）

满足以下**任一**可量化条件才立项：① 出现第三个写入进程；② 实时读端点超过 8 处（`_snap_fresh` 调用点计数），逐个改不划算；③ 实测飞书限流余量充足。在此之前不做。
