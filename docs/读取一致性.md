# 跨进程读取一致性

> 本文只维护**稳定规则**；端点、刷新间隔、文案等易变细节一律以代码为准（如刷新间隔见 `web/backend/app.py` 的 `_SNAPSHOT_INTERVALS`），变更功能无需同步本文。

## 现状模型

H5 后端把飞书各表全量刷进**进程内**快照 `_snapshot`，后台循环按 `_SNAPSHOT_INTERVALS` 定时刷新（各表间隔以代码为准）。

**bot 与 H5 是两个进程，内存不共享**：活动状态（`分组状态`、分组/一对一功能开关、一对一状态）、分组/一对一结果、各类开关由 bot 写入，H5 只读。H5 写完调 `refresh_snapshot_table_async` 只刷新自己进程内那份，对 bot 毫无作用——跨进程可见性只能靠 H5 重新读飞书。

> 分组写入方已不止 bot：H5 分组管理台后端（`/api/admin/group/*`）也会写 `分组状态` 与分组结果表，`分组状态` 为双写。即便如此也**不触发**失效通道立项条件——该条件要求的是「第三个」写入进程，而 bot 侧的分组读写**全部是即时读**（见「分组」节）。

## 规则一：决定性读取必须实时读

**任何端点，只要判定结果依赖 bot（或其他进程）写入的数据——活动状态、分组/一对一结果、各类功能开关——必须实时读飞书，不得吃周期快照。**

判定读取吃快照的代价不是「慢一点」而是**判错**：分组的「已完成」刚写进飞书，H5 快照还是「未开始」，用户点结果页就被拒，最长可达该表的背景刷新间隔。状态模型只有「未开始（空）/已完成」两态（收集中/已截止为历史遗留值，后端与 bot 已不再写）。

- `_snap_fresh(key)` / `snap_*(..., fresh=True)`：不管过没过期都实时读一次并回填。**决定性读取一律用这个。**
- `_snap_live(key)`：快照未就绪或过 `_SNAPSHOT_STALE` 时实时读一次**并回填**（自愈），不会每个请求都打飞书。

分组与一对一流程的全部判定端点（候选 / 志愿提交 / 状态 / 结果、「我的活动」入口等）均已实时化；用户端志愿选择统一走分组端点（志愿表同为 `GROUP_SELECT_TABLE`）；端点的具体清单以代码中 `_snap_fresh` 调用点为准。

## 实时读的失败冷却

`refresh_snapshot_table` 只在成功时刷新 `_snapshot_last_ok`，失败时旧时间戳留着；而 `_snap_live` / `_snap_fresh` 每次请求都会因「快照过期」再读一次飞书——飞书持续故障或限流（429）时，等于用请求量放大限流，正好是快照要避免的雪崩。

因此失败会拉起该表的冷却（常量 `SNAPSHOT_FAIL_COOLDOWN`，时长与取值理由见代码注释）：期间 `_snap_live` / `_snap_fresh` 直接返回现有快照、**不打飞书**（此时飞书本就不可用，返回陈旧快照是唯一合理降级），到期自动重试，不是永久熔断；任何一次读成功立即解除。冷却只压失败重试，**不压成功路径**，自愈不受影响。

## 决定性读取的并发去重：single-flight + 合并窗口

`_snap_fresh` 的语义是「判定前回到飞书」，但管理台首页一次加载会**并发**触发多条 fresh 读（活动总览 / 分组状态 / 未提交名单），同一张表被重复全表抓取，全部挤在飞书限流令牌桶后面排队，表现为页面加载明显变慢甚至 `Failed to fetch`。

因此 `refresh_snapshot_table(key, coalesce=0.0)` 加了两个机制：

- **single-flight**：per-key 互斥锁保证同一张表同一时刻最多一次 fetch 在途；后来者排队等它完成，再按自己的 `coalesce` 决定复用还是重抓，而不是各自再全表抓一遍。
- **合并窗口**：`_snap_fresh` 传 `SNAPSHOT_FRESH_COALESCE_SECONDS`——该表窗口内已**成功**抓过（`_snapshot_last_ok`）就直接复用。失败不写 `_snapshot_last_ok`，失败后的下一次调用必然重抓，与失败冷却（`SNAPSHOT_FAIL_COOLDOWN`）各管一段，互不遮蔽。

**为什么窗口不破坏「决定性读取」**：窗口只覆盖「同一屏并发请求」的时间尺度，远小于背景刷新间隔与 `_SNAPSHOT_STALE` 阈值。最坏情况是判定读到窗口之前的数据——而系统本就允许 `_snap_live` 在 stale 阈值内吃旧快照，窗口远严于既有容忍度；且这张表在窗口内刚被 fresh 读过并回填，不是「退回周期快照」，而是「并发读只读一次、结果共享」。**写后刷新**（`refresh_snapshot_table_async`）与背景 loop、全量刷新一律 `coalesce=0`：即使排队排在某个「写之前发起」的在途 fetch 后面，也一定会再抓一次，**写后快照不会停在写前状态**。

**锁顺序**：per-key 锁 → `_snapshot_lock`。任何路径都不得在持有 `_snapshot_lock` 时调用 `refresh_snapshot_table`，否则会与「持 per-key 锁、等 `_snapshot_lock`」的在途 fetch 形成 AB-BA 死锁。全部调用点已按此审计。

## 分组：H5 是第二个写入进程，但不需要失效通道

H5 分组管理台后端（`/api/admin/group/*`）会写 `分组状态` 与分组结果表，bot 也在写同一批栏位——`分组状态` 因此从 bot 单写变成双写。两端不会互相看不见：

- H5 执行分组后，bot 侧的分组读写（活动查询、结果幂等检查、清空结果）**全部走即时读**飞书 → 看得到最新状态与结果；
- 写冲突由 `lib.grouping.grouping_lock(activity_id)`（进程内线程锁 + 跨进程 flock，按活动分档）串行化；模式 flag 写入同样整段持锁（见下节）；
- `当前报名人数` / `活动状态` 仍只有 bot 轮询线程写；`update_record` 是 PUT 局部栏位更新（`lib/bitable_client.py` 只覆盖 body 里的栏位），不会擦掉 H5 写的分组栏位。

**结论：bot 端分组读写全部即时读，不需要任何失效通道**，与规则二一致。

> **H5 侧分组端点的约束（已落地）**：写端点走 `lib/grouping` + 跨进程活动锁；读端点一律 `fresh=True` 实时读并回填快照——正是规则一的落地。

## 模式 flag 互斥：单条记录 update 不是整笔事务

**曾被证伪的前提**：曾假定「飞书单条记录 update 是整笔事务」，据此认为并发模式切换的最终态必为一方「是」、另一方「否」，「双栏位单笔 PUT」即可保证 `分组功能开启` / `一对一功能开启` 的互斥，开关盲写即可、不需要锁。

**结论（决定性实验）**：同一记录并发两笔双栏位 PUT，实测可持久留下「双是」——飞书并发写是**栏位级交错**，单条记录 update 不是整笔事务。因此模式 flag 写入必须整段串行化，产品层保证来自 lib 写侧。

**现行保证机制（写侧串行化）**：模式 flag 的全部写入——`lib.grouping.set_group_flag`、`lib.grouping.set_mode`、`lib.onetoone.set_onetoone_flag`（开启走 `set_mode`；关闭独立写，不嵌套持锁）——整段（幂等判断 + 写；`activity` 缺省时的活动查询也在锁内）纳入既有的 per-activity 跨进程锁 `grouping_lock(activity_id)`（进程内线程锁 + `flock`，bot 与 H5 共用同一批 `yixianqian_grouping_<活动>.lock`）。两进程的 flag 写入互斥，不存在栏位级交错，最终态必为某一笔完整 payload。活动记录由调用端在锁外解析好（网络读不压在锁里）。

- **撞上执行作业快速失败**：分组/一对一 job 分钟级持同一把锁，flag 切换超时（`FLAG_LOCK_TIMEOUT`）即回 `BUSY`——H5 端点 409、bot 返回同语义提示；不长时间等待、不占请求/执行线程池。
- **写失败如实上报**：`update_record` 返回假 → `WRITE_FAILED`，H5 端点 500，绝不回 `{"ok": true}`；bot 渲染明确失败文案。
- **读接口不受影响**：`/activities` 等列表/读端点不取锁（快照或实时读），flag 写入的锁竞争不会让清单页卡住。
- **纯 client 直写不在保证内**：实验脚本直接对表双写只展示飞书行为，不是产品路径；产品层保证来自上述 lib 写侧串行化。

## 规则二：新跨进程写入功能，先在读取侧解决

优先在**读取侧**解决（判定处改实时读）。不要靠调小快照间隔（拿飞书配额赌一致性，且全局生效、误伤所有读路径），也不要先想加失效通道（跨进程协议，复杂度和故障面大一个量级）。

## 规则三：快照只用于展示类读取

只用于「展示类、低频、可容忍陈旧」的读取：卡片列表、我的报名列表、留言数等。陈旧只影响观感、不影响判定，也不该让用户重试才能推进。

回填快照**必须是全表形状**（统一走 `_SNAPSHOT_FETCHERS[key]` 的 `raw_search_records`），绝不能把 `get_group_results(act_id)` 这类按活动过滤过的结果写回全局快照，否则会污染成「只有某个活动的数据」。

## 什么时候才考虑统一失效通道（bot → H5 通知）

满足以下**任一**可量化条件才立项：① 出现第三个写入进程；② 实时读端点超过 8 处（`_snap_fresh` 调用点计数），逐个改不划算；③ 实测飞书限流余量充足。在此之前不做。
