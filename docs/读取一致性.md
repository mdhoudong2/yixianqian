# 跨进程读取一致性

## 现状

H5 后端把飞书各表全量刷进**进程内**快照 `_snapshot`，后台循环按 `_SNAPSHOT_INTERVALS` 刷新：likes/messages 20s、signups 45s、users 60s、activities 180s、observers 300s、group_selections / group_results / onetoone_selections / onetoone_results 300s（「收集中」状态已废除，四表不再因状态提速——历史遗留值只影响展示容忍，不影响刷新口径）。

**bot 与 H5 是两个进程，内存不共享**：活动状态（`分组状态`、分组功能开启、一对一状态）、分组/一对一结果、各类开关由 bot 写入，H5 只读。H5 写完调 `refresh_snapshot_table_async` 只刷新自己进程内那份，对 bot 毫无作用——跨进程可见性只能靠 H5 重新读飞书。

> **分组写入方自 H5 管理台后端 API 起变成两个（前端页面待后续 PR）。** H5 后端会写 `分组状态`、`每组男/女数`、`分组功能开启` 与分组结果表，与 bot 并列，`分组状态` 从「bot 单写」变成「双写」。即便如此也**不触发**下面的失效通道立项条件（第一条要求的是「第三个」写入进程），因为 bot 侧的分组读写**全部是即时读**——见下一节。

## 规则一：决定性读取必须实时读

**任何端点，只要判定结果依赖 bot（或其他进程）写入的数据——活动状态、分组/一对一结果、各类功能开关——必须实时读飞书，不得吃周期快照。**

判定读取吃快照的代价不是「慢一点」而是**判错**：分组的「已完成」刚写进飞书，H5 快照还是「未开始」，用户点结果页就被拒，最长 300s。状态模型只有「未开始（空）/已完成」两态（收集中/已截止为历史遗留值，后端与 bot 已不再写）。

- `_snap_fresh(key)` / `snap_*(..., fresh=True)`：不管过没过期都实时读一次并回填。**决定性读取一律用这个。**
- `_snap_live(key)`：快照未就绪或过 `_SNAPSHOT_STALE` 时实时读一次**并回填**（自愈），不会每个请求都打飞书。

已实时的分组流程端点：`group/candidates`、`group/select`、`group/status`、`group/result`、`/api/activities/mine/groups`。

已实时的一对一流程端点（2026-10-11 审核修复补齐）：`onetoone/result`（必聊名单；入口在「我的活动」/活动页）。用户端志愿选择已统一走分组端点（2026-10-15：原 `onetoone/candidates`、`onetoone/select`、`onetoone/status` 随 `onetoone_select` 死页删除，志愿表同为 GROUP_SELECT_TABLE、语义一致）；提交志愿的查重仍在跨进程活动锁内（`group/select` 的 file_lock；锁外查空的双击修复同款）；锁内的「状态==收集中」复核已随「志愿随时可改」方案移除（提交不再按状态拦截）。

## 实时读的失败冷却

`refresh_snapshot_table` 只在成功时刷新 `_snapshot_last_ok`，失败时旧时间戳留着；而 `_snap_live` / `_snap_fresh` 每次请求都会因「快照过期」再读一次飞书——飞书持续故障或限流（429）时，等于用请求量放大限流，正好是快照要避免的雪崩。

因此失败会拉起该表的冷却：`SNAPSHOT_FAIL_COOLDOWN = 30` 秒，期间 `_snap_live` / `_snap_fresh` 直接返回现有快照、**不打飞书**（此时飞书本就不可用，返回陈旧快照是唯一合理降级），到期自动重试，不是永久熔断；任何一次读成功立即解除。取 30 秒：飞书限流窗口通常在 1 分钟内，30 秒足够等到恢复又不至于长时间吃陈旧；且不小于任何一个 `_SNAPSHOT_STALE`（最短 likes/messages = 60s），不会额外拉长已有的陈旧上限。冷却只压失败重试，**不压成功路径**，自愈不受影响。

## 决定式读取的并发去重：single-flight + 2 秒合并窗口

`_snap_fresh` 的语义是「判定前回到飞书」，但管理台首页一次加载会**并发**触发多条 fresh 读
（活动总览 / 分组状态 / 未提交名单），同一张表被重复全表抓取 2–3 次，全部挤在 10 req/s
令牌桶后面排队：单页请求实测 4–20s，手机 / 飞书 webview 上网络换手即 `Failed to fetch`
（nginx 侧对应 499）。

因此 `refresh_snapshot_table(key, coalesce=0.0)` 加了两个机制：

- **single-flight**：per-key 互斥锁保证同一张表同一时刻最多一次 fetch 在途；后来者排队
  等它完成，再按自己的 `coalesce` 决定复用还是重抓，而不是各自再全表抓一遍。
- **合并窗口**：`_snap_fresh` 传 `SNAPSHOT_FRESH_COALESCE_SECONDS = 2.0`——该表 2 秒内已
  **成功**抓过（`_snapshot_last_ok`）就直接复用。失败不写 `_snapshot_last_ok`，失败后的
  下一次调用必然重抓，与失败冷却（`SNAPSHOT_FAIL_COOLDOWN`）各管一段，互不遮蔽。

**为什么 2 秒不破坏「决定性读取」**：窗口只覆盖「同一屏并发请求」的时间尺度，远小于背景
刷新间隔（20–300s）与 `_SNAPSHOT_STALE` 阈值（60–600s）。最坏情况是判定读到 2 秒前的
数据——而系统本就允许 `_snap_live` 在 stale 阈值内吃 60–600 秒的旧快照，2 秒远严于既有
容忍度；且这张表在这 2 秒内刚被 fresh 读过并回填，不是「退回周期快照」，而是「并发读只读
一次、结果共享」。**写后刷新**（`refresh_snapshot_table_async`）与背景 loop、全量刷新一律
`coalesce=0`：即使排队排在某个「写之前发起」的在途 fetch 后面，也一定会再抓一次，
**写后快照不会停在写前状态**。

**锁顺序**：per-key 锁 → `_snapshot_lock`。任何路径都不得在持有 `_snapshot_lock` 时调用
`refresh_snapshot_table`，否则会与「持 per-key 锁、等 `_snapshot_lock`」的在途 fetch 形成
AB-BA 死锁。已逐一核对全部调用点（`_snap_live`、`_snap_fresh`、`_snapshot_loop`、
`refresh_snapshot`、`refresh_snapshot_table_async`、各写端点、`_photo_writer`、资料保存的
同步刷新）：均不持 `_snapshot_lock` 调用。

## 分组：H5 是第二个写入进程，但不需要失效通道

H5 分組管理台後端（`/api/admin/group/*`）会写 `分组状态` 与分组结果表，bot 也在写同一批栏位——`分组状态` 因此从 bot 单写变成双写。逐条核对过（基于 Phase 1 已就位的 `lib/grouping` 接线），两端不会互相看不见：

| 场景 | 结论 |
|---|---|
| H5 执行分組，bot 发「分组状态 A-0002」 | bot 走 `find_activity_by_id`（`bot/queries.py`）**即時讀**飛書 → 看得到最新状态 ✅ |
| H5 执行分組，bot 发「执行分组 A-0002 3 3」 | bot 的幂等检查 `search_records(GROUP_RESULT_TABLE, …)` 也是**即時讀** → 看得到 H5 刚写的本轮结果 → 正确拦下 ✅ |
| H5 执行分組，bot 发「清空分组结果 A-0002」 | 同样是即時讀 + 删除全部历史结果 ✅ |
| 写冲突本身 | 分组**执行/清空**路径两端都持 `lib.grouping.grouping_lock(activity_id)`（进程内线程锁 + 跨进程 flock，按活动分档），写同一场分組由此串行化。**模式 flag 写入**（`分组功能开启` / `一对一功能开启`）同样整段持这把锁——见下方「模式 flag 互斥」节（2026-10-12 修正） |
| 模式 flag 写入（`分组功能开启` / `一对一功能开启`） | 整段持锁（2026-10-12 修正）：飞书单条记录 update **不是**整笔事务，两笔并发双栏位 PUT 会栏位级交错并持久留下「双是」（决定性实验 28/30）。旧前提「盲写后写者胜、不需要锁」已证伪——见下方「模式 flag 互斥」节 |

`当前报名人数` / `活动状态` 仍只有 bot 轮询线程写，而 `update_record` 是 PUT 局部栏位更新
（`lib/bitable_client.py` 只覆蓋 body 里的栏位），不会擦掉 H5 写的分組栏位。

**结论：bot 端分組讀寫全部即時讀，不需要任何失效通道**，与规则二一致。

> **H5 侧分组端点的约束（已落地）。** H5 分組管理台後端 API（`/api/admin/group/*`）已落地：寫端點走 `lib/grouping` + 跨進程活動鎖；讀端點一律 `fresh=True` 實時讀並回填快照——活動總覽讀 `activities`/`group_selections`/`group_results`，分組狀態另讀 `signups`，未提交名單讀 `activities`/`group_selections`/`signups`。這正是上面規則一的落地。前端頁面待後續 PR。

## 模式 flag 互斥：单条记录 update 不是整笔事务（2026-10-12 修正）

**已证伪的旧前提**：此前 `lib/grouping.py` 与设计书假定「飞书单条记录 update 是整笔事务」，据此认为并发模式切换的最终态必为一方「是」、另一方「否」，「双栏位单笔 PUT」即可保证 `分组功能开启` / `一对一功能开启` 的互斥不变量，分组/一对一开关是盲写、不需要锁。

**决定性实验**（2026-10-12，测试 base，空值活动 A-0016/A-0017，纯 client 直写）：同一记录并发两笔双栏位 PUT（(是,否) × (否,是)），30 轮中 **28 轮**留下持久的「双是」，最终态不等于任一 payload——飞书并发写是**栏位级交错**，单条记录 update 不是整笔事务。上一次修复（写入侧 schema 级 `field_exists` 合写）仍挡不住交错：经端点（group/flag × activity/mode 并发）实测 1/3 轮复现「双是」。

> **复现前提与起始值（2026-10-12 审计补记）**：上述「双是」复现的前提是**每轮先复位为非空的 `(否,否)`** 再并发双写（区别于真空值 `("","")` 起跑）。审计以同法（NO-LOCK 对照）复测 30 轮，**29 轮**复现（`mutation_values_a0016.log`）；而改以真空值 `("","")` 起跑、同样无锁，审计合计 **44 轮 0 复现**（`mutation_empty_extra` 15 轮、`atomic_empty_reset` 纯 client 10 轮完整跑完；`mutation_a0016` 12 轮、`mutation_barrier_a0016` 7 轮为中断留存样本，均无异常）。即危害复现与**起始值强相关**：后人重跑「空值版本」得到 0 复现时，不应据此否定本节的 28/30——该现象的前提是「每轮先复位 `(否,否)`」。

**现行保证机制（写侧串行化）**：模式 flag 的全部写入——`lib.grouping.set_group_flag`、`lib.grouping.set_mode`、`lib.onetoone.set_onetoone_flag`（开启走 set_mode；关闭独立写，不嵌套持锁）——整段（幂等判断 + 写；`activity` 缺省时的活动查询也在锁内）纳入既有的 per-activity 跨进程锁 `grouping_lock(activity_id, timeout=FLAG_LOCK_TIMEOUT=5)`（进程内线程锁 + `flock`，bot 与 H5 共用同一批 `yixianqian_grouping_<活动>.lock`）。两进程的 flag 写入互斥，不存在栏位级交错，最终态必为某一笔完整 payload。活动记录由调用端在锁外解析好（沿用既有约定：网络读不压在锁里；真实 base 的「活动ID」是自动编号，按字符串过滤查不到，必须传记录）。

- **撞上执行作业快速失败**：分组/一对一 job 分钟级持同一把锁，flag 切换 5 秒拿不到即回 `BUSY`——H5 端点 409（「当前有分组/一对一任务在执行中，请稍候再试」），bot 同文案；不长时间等待、不占请求/执行线程池。
- **写失败如实上报**：`update_record` 返回假 → `WRITE_FAILED`，H5 端点 500，绝不回 `{"ok": true}`；bot 渲染明确失败文案（`set_group_flag` 原先忽略返回值，已修）。
- **读接口不受影响**：`/activities` 等列表/读端点不取锁（快照或实时读），flag 写入的锁竞争不会让清单页卡住。
- **纯 client 直写不在保证内**：如 `atomic_direct` 那类实验脚本直接对表双写，只是展示飞书行为，不是产品路径；产品层保证来自上述 lib 写侧串行化。

## 规则二：新跨进程写入功能，先在读取侧解决

优先在**读取侧**解决（判定处改实时读）。不要靠调小快照间隔（拿飞书配额赌一致性，且全局生效、误伤所有读路径），也不要先想加失效通道（跨进程协议，复杂度和故障面大一个量级）。

## 规则三：快照只用于展示类读取

只用于「展示类、低频、可容忍陈旧」的读取：卡片列表、我的报名列表、留言数等。陈旧只影响观感、不影响判定，也不该让用户重试才能推进。

回填快照**必须是全表形状**（统一走 `_SNAPSHOT_FETCHERS[key]` 的 `raw_search_records`），绝不能把 `get_group_results(act_id)` 这类按活动过滤过的结果写回全局快照，否则会污染成「只有某个活动的数据」。

## 什么时候才考虑统一失效通道（bot → H5 通知）

满足以下**任一**可量化条件才立项：① 出现第三个写入进程；② 实时读端点超过 8 处（`_snap_fresh` 调用点计数），逐个改不划算；③ 实测飞书限流余量充足。在此之前不做。
